# Test Case Writing

A Test Case is a detailed document outlining the steps, conditions, and expected results for testing a specific functionality or feature of a system.

---

# Components of a Test Case

## 1. Test Case ID
A unique identifier (e.g., `TC_001`).

## 2. Test Case Title
Brief description of the test case.

## 3. Preconditions
Requirements that must be met before executing the test.

## 4. Test Steps
Step-by-step instructions to execute the test.

## 5. Test Data
Data required for testing.

## 6. Expected Result
The expected outcome after performing the steps.

## 7. Actual Result
The result after executing the test (filled during execution).

## 8. Status
Pass, Fail, or Blocked.

## 9. Priority
Importance of the test case (High, Medium, Low).

---

# Example Test Case

| Field | Details |
|---|---|
| Test Case ID | TC_001 |
| Title | Verify Login with Valid Credentials |
| Preconditions | User must be registered in the system |
| Test Steps | 1. Open the login page.<br>2. Enter valid credentials.<br>3. Click "Login." |
| Test Data | Username: user123<br>Password: Pass@123 |
| Expected Result | User is redirected to the dashboard. |
| Actual Result | User is redirected to the dashboard. |
| Status | Pass |
| Priority | High |

# Test Scenario Drafting

A Test Scenario is a high-level description of what to test. It focuses on verifying a functionality or feature.

---

# Steps to Draft Test Scenarios

1. Understand requirements thoroughly.
2. Identify functionalities or features to be tested.
3. Divide functionalities into logical modules.
4. Write test scenarios for each module.

---

# Example Test Scenarios

## Feature: User Login

- Verify login with valid credentials.
- Verify login with invalid credentials.
- Verify login when the username or password field is left blank.
- Verify the "Forgot Password" functionality.

# Requirement Traceability Matrix (RTM)

The Requirement Traceability Matrix is a document that maps requirements to their corresponding test cases, ensuring complete coverage.

---

# Purpose of RTM

- Ensure all requirements are tested.
- Identify missing or redundant test cases.
- Track the status of each requirement.

---

# RTM Template

| Requirement ID | Requirement Description | Test Case ID(s) | Status |
|---|---|---|---|
| R_001 | Login functionality | TC_001, TC_002 | Passed |
| R_002 | Password reset | TC_003 | Failed |

# Bug Drafting and Reporting

A Bug Report documents a defect in the software and communicates it to the development team for resolution.

---

# Components of a Bug Report

## 1. Bug ID
Unique identifier (e.g., `BUG_001`).

## 2. Summary
A brief description of the defect.

## 3. Steps to Reproduce
Detailed steps to recreate the issue.

## 4. Expected Result
What should happen.

## 5. Actual Result
What actually happens.

## 6. Severity
Impact on the system (Critical, High, Medium, Low).

## 7. Priority
Fix urgency (High, Medium, Low).

## 8. Environment
Browser, OS, and version details.

## 9. Attachments
Screenshots, logs, or video evidence.

---

# Example Bug Report

| Field | Details |
|---|---|
| Bug ID | BUG_001 |
| Summary | Login button not functional |

| Priority | High |
| Environment | Chrome 115.0.1, Windows 10 |
| Attachments | Screenshot of the issue attached |

# Test Drafting Template

## Generic Test Case Template

| Field | Description |
|---|---|
| Test Case ID | Unique identifier for the test case |
| Title | A short description of the test |
| Module/Feature | The functionality being tested |
| Preconditions | Any setup or prerequisites needed before running the test |
| Test Steps | Step-by-step instructions to execute the test |
| Test Data | Specific data required for the test |
| Expected Result | The expected outcome of the test |
| Actual Result | The observed outcome after running the test (filled later) |
| Priority | Importance of the test case (High, Medium, Low) |
| Status | Pass, Fail, Blocked, etc. |
| Remarks | Additional notes or comments |
