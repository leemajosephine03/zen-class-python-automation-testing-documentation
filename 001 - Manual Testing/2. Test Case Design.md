# SDLC Models

## 1. Waterfall Model

### Definition
A sequential, phase-wise model where each phase starts only after the previous one is completed.

### Advantages
- Simple and easy to understand.
- Ideal for small projects with clear requirements.

### Disadvantages
- Inflexible; changes are difficult to accommodate.
- Testing occurs only after development is complete.

---

## 2. V-Model (Verification and Validation Model)

### Definition
An extension of the Waterfall Model where each development phase has a corresponding testing phase.

### Advantages
- Early detection of defects.
- Ensures quality at every stage.

### Disadvantages
- Inflexible and not suitable for complex or dynamic projects.

---

## 3. Agile Model

### Definition
An iterative and incremental model that focuses on collaboration, customer feedback, and adaptability.

### Advantages
- High flexibility to changes.
- Continuous delivery of working software.

### Disadvantages
- Requires close collaboration with the client.
- Documentation may be minimal.

---

## 4. Spiral Model

### Definition
A risk-driven iterative model that combines elements of Waterfall and Prototyping.

### Advantages
- Effective for managing risks.
- Suitable for large, complex projects.

### Disadvantages
- High cost and time-consuming.
- Requires expertise in risk analysis.

---

# Test Case Design Techniques

## 1. Static Techniques

### Definition
Involve reviewing documents, code, or requirements without executing the system.

### Examples
- Code reviews
- Walkthroughs
- Inspections

---

# Dynamic Testing Techniques

## 1. Equivalence Partitioning (EP)

### Definition
Divides input data into partitions or classes where all values in a partition are expected to behave similarly. Only one representative value from each partition is tested.

### Purpose
Reduce the total number of test cases by focusing on representative values.

### Example
Suppose a field accepts numbers between 1 and 100.

#### Valid Partition
- 1 to 100 (e.g., test with 50)

#### Invalid Partitions
- Less than 1 (e.g., 0)
- Greater than 100 (e.g., 101)

### Test Cases
- Input = 50 (valid)
- Input = 0 (invalid)
- Input = 101 (invalid)

---

## 2. Boundary Value Analysis (BVA)

### Definition
Focuses on testing values at the edges or boundaries of input ranges since defects often occur there.

### Purpose
Identify errors at boundary conditions (minimum and maximum).

### Example
For a field that accepts numbers from 1 to 100, test the following boundary values:

#### Lower Boundary
- 0
- 1
- 2

#### Upper Boundary
- 99
- 100
- 101

### Test Cases
- Input = 1 (valid, lower boundary)
- Input = 100 (valid, upper boundary)
- Input = 0 (invalid, just below lower boundary)
- Input = 101 (invalid, just above upper boundary)

---

## 3. Decision Table Testing

### Definition
Represents test scenarios as combinations of inputs (conditions) and their corresponding outputs (actions).

### Purpose
Identify all possible combinations of inputs to ensure comprehensive coverage.

### Example
Suppose an online shopping app offers a discount based on the following conditions:

- Condition 1: Member status (Yes/No)
- Condition 2: Order value >= Rs100 (Yes/No)
- Output: Discount is given or not

### Decision Table

| Member | Order >= Rs100 | Discount |
|--------|----------------|----------|
| Yes | Yes | Yes |
| Yes | No | No |
| No | Yes | No |
| No | No | No |

### Test Cases
- Member = Yes, Order = Rs150 → Discount = Yes
- Member = No, Order = Rs50 → Discount = No

---

## 4. State Transition Testing

### Definition
Focuses on testing system behavior for different states and transitions based on events or conditions.

### Purpose
Ensure correct state changes under different input conditions.

### Example
ATM transaction states:

- State 1: Idle
- State 2: Card Inserted
- State 3: PIN Verified
- State 4: Transaction Completed

### State Transitions
- Event: Insert Card → Transition from Idle to Card Inserted
- Event: Enter PIN → Transition from Card Inserted to PIN Verified
- Event: Complete Transaction → Transition from PIN Verified to Transaction Completed

### Test Cases
- Insert card and enter valid PIN → Transition to Transaction Completed
- Insert card and enter invalid PIN → Transition back to Card Inserted state

---

## 5. Use Case Testing

### Definition
Tests the end-to-end functionality of a feature based on specific use cases.

### Purpose
Validate the system’s behavior under real-world scenarios.

### Example
Use case: Booking a flight ticket on an airline website.

### Steps
1. Search for flights
2. Select a flight
3. Enter passenger details
4. Make payment

### Test Cases
- Perform the entire booking process with valid inputs → Success
- Enter invalid payment details → Booking fails

---

## 6. Ad-Hoc Testing (Experience-Based)

### Definition
Informal and unstructured testing based on tester’s intuition and experience.

### Purpose
Identify issues that formal test cases might miss.

### Example
While testing a shopping cart feature, the tester decides to:
- Add items to the cart, then remove them.
- Refresh the browser midway and check the cart state.
- Enter invalid coupon codes to observe system response.
